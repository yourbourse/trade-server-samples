# Generated C# API Client

This project calls the Trade Server public and admin REST APIs through C# clients generated by [Kiota](https://learn.microsoft.com/openapi/kiota/). You don't write request or response classes by hand.

Every build downloads the current API specs from the docs site and regenerates the clients when a spec has changed. Your code always compiles against the API as it is today. When the API changes in a way that affects your code, you get a compile error instead of a surprise at run time.

## Requirements

- .NET 10 SDK
- The login for the docs site, the one you use to open https://docs.yourbourse.trade/api/

## Setup

1. Set the docs site login as environment variables.

   macOS and Linux:
   ```bash
   export TRADE_SERVER_DOCS_USER="your-user"
   export TRADE_SERVER_DOCS_PASSWORD="your-password"
   ```

   Windows (PowerShell), saved for new terminals and IDEs:
   ```powershell
   setx TRADE_SERVER_DOCS_USER "your-user"
   setx TRADE_SERVER_DOCS_PASSWORD "your-password"
   ```
   Restart your terminal or IDE afterwards so it picks them up.

   The build downloads from `https://docs.yourbourse.trade`. To use a different docs site, also set `TRADE_SERVER_DOCS_URL`.

   On a build server, such as a CI pipeline, store the same two variables as secrets, so its builds also compile against the current API.

2. Open `Program.cs` and fill in your Trade Server URLs and logins:
   ```csharp
   const string publicApiUrl = "https://yourbourse.trade:2xxxx";
   const long login = 1;
   const string password = "xxx";

   const string adminApiUrl = "https://yourbourse.trade:2xxxx";
   const long managerLogin = 1;
   const string managerPassword = "xxx";
   ```
   `login` must be a trading account, because the public API signs in trading accounts. A manager login there fails with `HTTP 400: Invalid parameter`. `managerLogin` is the manager you sign in with on the admin API.

   The admin part creates, edits and deletes holidays (see [Changing Data](#changing-data)). Point it at a dev server.

## Build and Run

```bash
cd csharp/generated-api-client
dotnet run
```

The first build installs Kiota, at the version pinned in `.config/dotnet-tools.json`, and generates the clients into `Generated/`. That folder is not committed. Open it to see what was generated.

## What Happens on Each Build

| Step | What it does |
| ----- | ----- |
| Download | Fetches `api/openapi.yaml` and `admin-api/openapi.yaml` from the docs site into `obj/trade-server-specs/`. |
| Generate | Runs Kiota only when a spec, the project file or the Kiota version changed since the last build. |
| Compile | Builds your code together with `Generated/`. |

If the download fails, for example because there's no network or the password is wrong, the build warns you and uses the specs from the last successful download. If there's no earlier download yet, the build stops with an error saying what to set.

To see Kiota's own output, for example when generation fails, build with `dotnet build -v n`.

The build reads the password straight from the environment, so it never shows up in build logs.

## Authentication

`SigningHandler` adds the `X-YB-API-Key` header to every request. It also signs every `POST`, `PUT` and `DELETE` with the timestamp method. It signs the exact body that goes out, so the signature always matches. For the nonce method, see [api-example](../api-example).

`TradeServerSession` holds the keys the handler uses. Requests are signed with your password until you sign in. After that, they use the API key and signing token that `authorize` returns:

```csharp
var session = new TradeServerSession(password);
var publicApi = new PublicApiClient(CreateRequestAdapter(publicApiUrl, session));

var token = await publicApi.Authorize.PostAsync(new() { Login = login });
session.SignIn(token!.Token!, token.SigningToken!);
```

## Using the Clients

- **Paths become properties.** `GET /symbols/query` is `publicApi.Symbols.Query.GetAsync()`.
- **Query parameters** are typed: `config.QueryParameters.MaxResults = 100`.
- **Header parameters are not typed.** Add them yourself. For example, to request the next page:
  ```csharp
  var page = await publicApi.Symbols.Query.GetAsync(config =>
      config.Headers.Add("X-YB-NEXT-TOKEN", nextToken));
  ```
- **Errors** come back as exceptions. When the spec describes the error body, you get `ProblemDetails`, which has `Title` and `Detail`. Otherwise you get Kiota's `ApiException`. `ProblemDetails` has no message of its own, so print `Title` and `Detail` yourself, as `Program.cs` does.
- **Property names follow the JSON names**, so `b` becomes `B`. Hover over a property in your IDE to see its description. When two JSON names differ only by case, such as `s` (symbol) and `S` (side), Kiota adds the class name to one of them: `order.S` is the symbol and `order.OrderS` is the side.

## Changing Data

`HolidayExample.cs` runs a full cycle on holidays through the admin API. First it works with one holiday: create, read, edit, find it in the list, then delete. Then it creates two holidays in one call and deletes both in one call.

The holidays it creates are disabled, dated 2099 and match no symbol, so they never close trading. The single holiday is deleted in a `finally` block, so it's removed even when a step in between fails.

- **Create** by sending `Id = 0` and `Version = 0`. The response holds the new id and version.
- **Edits and deletes** must send the current version in the `If-Match` header. Read it from the `ETag` header of a `GET`:
  ```csharp
  var headers = new HeadersInspectionHandlerOption { InspectResponseHeaders = true };
  var holiday = await holidays.GetPath[id].GetAsync(config => config.Options.Add(headers));
  var etag = headers.ResponseHeaders["ETag"].Single();

  await holidays.Edit.PostAsync(holiday!, config => config.Headers.Add("If-Match", etag));
  ```
- **Batch calls** don't use `If-Match`. Each item carries its own version, and each item succeeds or fails on its own, so check the `S` flag of every result even when the call as a whole succeeds.

## Retries

Only `429 Too Many Requests` is retried, after the `Retry-After` delay. Kiota would normally retry `503` and `504` too. The server may already have acted on those requests, so a retried order could be placed twice.

## Using This in Your Own Project

1. Copy `TradeServerClients.targets`, `.config/dotnet-tools.json`, `SigningHandler.cs` and `TradeServerSession.cs` into your project folder.
2. Add these to your `.csproj`:
   ```xml
   <ItemGroup>
       <PackageReference Include="Microsoft.Kiota.Bundle" Version="2.1.2" />
   </ItemGroup>

   <Import Project="TradeServerClients.targets" />
   ```
3. Add `Generated/` to your `.gitignore`.

The generated clients go into `<YourRootNamespace>.PublicApi` and `<YourRootNamespace>.AdminApi`.

To move to a newer Kiota, change the version in `.config/dotnet-tools.json`. The next build regenerates both clients. Update `Microsoft.Kiota.Bundle` at the same time.
